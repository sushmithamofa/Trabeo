CAD-to-Revit app: what it does, what’s wrong, what to improve
1. What the app does today

It turns a DWG drawing set into a structural model, in five steps:

Step	What happens	Main code
1. Convert	DWG → DXF through ZWCAD, cached in the project folder	cad2revit/core/dwgconv.py
2. Split and classify	Splits each drawing into views (layouts, or areas of model space). Then decides what each view is (plan, beam details, schedule, legend…) from title words and what’s drawn	building/sheets/
3. Read	The plan reader (the old extractor) finds columns, beams, slabs, openings and sunk zones. It does this mainly by layer name: config.json maps layer names to roles, and a “suggested profile” guesses roles for unknown layers. Other readers pull sizes from captions, tables, section details and layer names	cad2revit/core/extract.py (2,400 lines), building/readers/
4. Link and resolve	Attaches marks to elements, attaches sizes to marks, and scores each value by source (schedule 1.0 … layer name 0.6). Agreement → “read”, disagreement → “conflict”, nothing → “missing”	building/linker.py
5. Review and output	A web review where a person settles values. Then output to Revit (IronPython scripts run inside Revit, through the MCP plug-in or Rhino.Inside), IFC, or a Rhino .3dm	webapp.py, building/export.py, revit/build_model.py

Worth keeping:

The evidence model: every value records its source, layer and CAD handle.
The rule that nothing unsettled gets built silently.
The review screen, and the IFC and Rhino outputs that don’t need Revit.
The selftests.

That foundation is sound.

2. What logic is wrong (the root causes behind the New block errors)

A. Recognition is driven by layer names, not by what’s drawn.

An element only exists if its layer is mapped. Every new consultant means new layer names, so the app falls back on guessing (profiles/suggest.py). The “res” project runs with suggested: true, which means unconfirmed guesses are building the model.
Example: S-B5-230X600 is a beam-size layer name, but on that layer were rebar symbols, which the app correctly ignored. The Steel Col block, meanwhile, was half used: its “SC1” labels went onto the concrete columns.
Layer names should be one piece of evidence, not the gate.

B. Fixes pile up drawing by drawing, so the rules are overfitted.

The non-test code has 151 comments naming specific drawings (“Wing B”, “Sasan Gir”, “New block”…).
extract.py runs a fixed chain of about 30 patch passes: _merge_face_pairs, _drop_orphan_faces, _bridge_staggered_faces, _align_face_continuations, _extend_beams_to_supports and so on. Each was added to fix one case, and each depends on the order of the others.
That’s why every new drawing produces a fresh list of errors, and why each fix has to be kept “narrow” to protect the baselines.
The baselines lock in current behaviour, including its mistakes, rather than checking against a correct answer.

C. There are two models and two sets of rules.

The old extractor produces its own Result → model.json. The newer building.json (with evidence) sits on top of it, and export.py then rewrites model.json.
The two sets of rules contradict each other. The slab module’s own description says “A bay with no mark is left open… Nothing is invented”, but the code at slabs.py:506 copies the nearest mark into unmarked bays. That’s how the Main Block area got NS1, NS2, NS4 and NS5.
The linker’s “never guess” rule doesn’t reach inside the extractor.

D. Beam geometry is rebuilt with loose snapping.

Beams are rebuilt by pairing face lines, then joining, extending and trimming with tolerances up to 800 mm.
That produces 115-wide and 450-wide beams where the layer says 150 and 300, beams carried on “as far as the face is drawn”, and staggered-face bridging.
No step checks the result against structural sense: a beam spans from support to support, and a column is at least about 200 mm.

E. The value resolver hides conflicts.

In linker.py:977-984, if the strong sources agree, a disagreeing layer name or measured size is treated as a note only.
So NB3 drawn on a 230X900 layer but captioned 750 shows as plain “read”. The engineer never sees that the drawing contradicts itself.
When the only sources are measured size and layer name, and they disagree, the result is “read” at confidence 0.4 instead of “conflict”.

F. There is no idea of scope (what belongs to this model).

The app reads everything on a plan as this floor’s structure.
It has no step for the building’s outline, existing or neighbouring blocks (the “Main Block” hatch), pasted blocks that don’t fit (the steel-column block runs 9 m past the plan), or sections used for reference.

G. Things that were dropped never show up in review.

The review only draws extracted elements, so the 6 dropped columns were invisible. The only trace was a “blocker: open by 750 mm” message in a list.
If you can’t see the raw CAD under the model, you can’t spot what’s missing.

H. Small geometry bugs.

The closed-outline check runs after the closing point has already been removed (6 columns lost).
Touching rectangles aren’t merged (70×600 slivers built as columns).
Labels stacked on the same spot still split beams.

I. Floor alignment and setting out are fragile. With no grid, the base point is “SW corner of this floor’s columns” (config.json base_point: auto). If one floor’s column set differs (say a column was dropped), its origin can shift relative to the other floors. I haven’t confirmed whether export applies one shared origin across floors; it’s worth checking.

3. What should change so it can read any structural CAD
One pipeline, one model. Make building.json the only model. Have the extractor produce candidates with evidence and never final elements, marks or sizes. The resolver applies one rulebook, including “never invent”, everywhere. model.json becomes only an output format.
Recognise by what’s drawn first, with layer and name as supporting evidence. For each entity or group, score features:
Shape: closed rectangle size, parallel pairs and their spacing.
Linetype: beams below a slab are often dashed.
Hatch inside or not, colour, block name, nearby text.
Layer name.

Combine the scores into one classification. The review decisions you’ve collected are labelled data, so later a trained classifier could replace the hand-written rules.

A structural graph step. Columns and walls are nodes, and beams are edges between supports. Slabs are the closed faces of that network; the app already derives slabs from bays, but it should do so from a clean graph. Then validate:
Every beam has two supports.
No member is below a minimum size.
Columns line up from floor to floor.
Beam width matches its layer and caption.

Anything that fails goes into the decision queue. This one general step replaces most of the 30 patch passes.

A scope step before reading. Work out the building outline. Mark regions as existing or other block (hatches or titles like “Main Block” / “Existing”), reference-only views, and pasted debris. Exclude them or label them, never model them quietly.
Make conflicts visible. Any source that disagrees, including the layer name, becomes a conflict for the user, with a one-click “use this value”.
Show the CAD under the model in Review. Add a layer of “structural geometry the app did not use”. It would have caught the dropped columns at a glance, much like the overlay picture I made.
Test against correct answers, not just against the app’s past output.
Keep the baselines, but add hand-checked answer sets from 10+ different consultants. tools/scorecard.py already starts this.
Report per element type: found, wrong, missed, flagged.
The key number is “silently wrong” (built wrong with no flag), and it must be zero.
Setting out. Read grids where they exist. Where they don’t, ask once for a shared reference point and use it for every floor.
4. The Revit and Rhino side
Revit: the current route runs IronPython scripts inside Revit through MCP send_code plus Rhino 8’s IronPython. It works, but it’s fragile. Better options:
A small C# Revit add-in or pyRevit extension that reads the neutral model.
A family and type mapping table: mark/size → Revit family and type, the company standard.
IFC as the main neutral output. Revit, Rhino, Tekla and ETABS all import it. You already write IFC4 without a library; keep it and test it in Revit.
Rhino: the hand-written .3dm writer is fine. The official rhino3dm library would be a sturdier alternative if problems show up.
DWG conversion depends on ZWCAD. The free ODA File Converter is a common replacement that doesn’t need a CAD program open.
5. Suggested order
Fix the New block bugs already in the handoff (#2, #3, #5, #4, #6). These are quick and low-risk.
Make conflicts visible (point E) and add the CAD underlay to Review (point 6). Both are cheap and make every later error easier to see.
Add the scope step (point 4) and enforce “never invent” in the slab code.
Build answer sets from other consultants’ drawings and measure.
Then the bigger rework: one pipeline, then shape-first recognition, then the structural graph. Do it step by step, keeping the old path until the scorecards show the new one is at least as good.

The main point: the app has a strong framework (evidence, review, don’t guess), but recognition is built on layer names plus case-by-case patches. That’s why each new drawing breaks in new ways. Reading any consultant’s drawings needs recognition from shape and structure, a single rulebook, and testing against correct answers.
